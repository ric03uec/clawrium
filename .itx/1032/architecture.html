01 / System boundaries

Clawrium grants access. Pi uses it.

Provider choice, model mapping and credential source live in the Clawrium control plane. Clawrium provisions the selected model and scoped access onto the fleet host; Pi consumes that provisioned access when invoked.

Provisioning: Clawrium resolves provider, model and agent-scoped authentication, then syncs those onto the host. Execution: CLI or GUI → Clawrium chat adapter → Pi in its OS account → inference using the already-authorized model endpoint. Pi does not discover providers or ask the control plane for an access grant. Responses return to the same chat surface.
No persistent process

No daemon, service, gateway, tunnel or reserved port; service controls report not applicable.

Clear ownership

The Pi manifest has chat capability but no web UI. Clawrium owns agent-level files; project-level .pi stays operator-owned.

Secret boundary

Provider records stay in the control plane; only scoped access reaches the host. No secrets in fleet metadata, diffs or logs.

02 / Operator journey

Four lifecycle moments

Create installs the binary and account. Clawrium's configuration injects the selected model and scoped access. Conversation processes start only when requested.

01

Create

clawctl agent create <name> --type pi --host <host> provisions a dedicated account and pinned installation. No login or inference yet.

02

Configure & sync

Attach a supported provider and model; render only bounded agent settings and the selected credential mode.

03

Chat & exec

CLI and GUI start a bounded Pi invocation on demand; session continuity and reset work without a service.

04

Remove

Verify ownership, clean remote Pi-owned resources first, then delete per-instance local state and secrets.

Native UI boundary: GUI chat is Clawrium's chat view. agent open and the “Open Agent UI” button remain unavailable because Pi does not provide a native web dashboard.
03 / Provider contract

Three control-plane choices. One Pi.

Clawrium selects and provisions one supported provider/model and its scoped access. Pi uses the assigned model. Each choice has a separate live-response gate.

First · baseline

OpenRouter

04 / Customer-verifiable delivery

A usable outcome at every step

Each milestone has an operator action, the work needed to unlock it, and a live acceptance check. These are planned outcomes, not completed features.

  1. I can install and inspect Pi on a host

    Try it: Create Pi on Linux and macOS, list the agent, then run clawctl agent exec <name> -- --version.

    Execute: Pin Pi, add its manifest and per-OS install/exec playbooks, provision a dedicated OS user, wire fleet views and mark service controls not applicable.

    Pass → pinned version runs on both hosts; no login, service, port or native dashboard; existing agents unaffected.

  2. I can ask my OpenRouter model a question in the CLI

    Try it: Attach an existing provider, select a model, sync, then use CLI chat and native exec for a real reply on i-wolf. Follow up in the same session.

    Execute: Validate Pi's model mapping, provision the selected model and agent-scoped key, and build bounded on-demand chat, exec, streaming and session continuation/reset.

    Pass → live response and continued session through Pi; no manual host-side provider setup. #1038 ↗

  3. I can chat with the same agent in the GUI

    Try it: Send a message in Clawrium's GUI, continue the conversation, clear history and start a new one.

    Execute: Connect GUI chat to the same provisioned model and on-demand Pi adapter, show provider/model and redact errors. Leave the native Open Agent UI action unavailable.

    Pass → real GUI response, continuation and reset with the same OpenRouter selection; no Pi daemon.

  4. I can use my AWS SSO-backed Bedrock model

    Try it: Select Bedrock in Clawrium, sync and chat in CLI and GUI; repeat after credentials expire and refresh or re-login.

    Execute: Validate Pi's Bedrock model/region/profile contract; provision only this agent's scoped AWS access and surface expiry clearly.

    Pass → live replies before and after refresh/re-login; expired access fails explicitly. #1039 ↗

  5. I can use my Codex OAuth-backed model

    Try it: Select Codex, complete the supported login handoff, then get real CLI and GUI replies; repeat after refresh/re-login.

    Execute: Validate Pi-native openai-codex OAuth and narrow control-plane-to-host credential handoff; exercise native exec and both chat surfaces.

    Pass → authenticated OAuth replies and verified renewal; an API-key response does not count. #1040 ↗

  6. I can switch providers and remove Pi safely

    Try it: Switch and detach providers, confirm old access no longer works, remove Pi and inspect the host and remaining agents.

    Execute: Remove stale agent-local credentials without revoking shared provider credentials; add ownership-checked remote-first cleanup, cover both OSes with focused tests, run make test and make lint, and publish operator docs/changelog.

    Pass → no stale access or unrelated fleet changes; operator-owned project .pi files remain intact.
Validate the contract before each live gate

Confirm Pi's pinned model mapping, session/streaming behavior and provider-specific credential handoff before exposing each customer workflow. A configured provider alone is not a model response; keep secrets and prompt-bearing runner artifacts private.
